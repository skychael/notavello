How to read rate limit headers and back off correctly

APIs protect shared resources with rate limits that vary by endpoint, HTTP method, tenant, and time window. A client that ignores the headers returned with every response will hit 429 responses repeatedly, while one that reads those headers can pace itself, back off only the affected scope, and continue working on other parts of the API. The difference shows up in reliability during traffic spikes or when multiple instances share the same quota.

Common rate limit headers and what they mean

Most APIs return headers that describe remaining capacity or the time until the window resets. GitHub uses x-ratelimit-remaining and x-ratelimit-reset in UTC epoch seconds. Jira Cloud returns RateLimit-Reason on 429 responses to indicate whether the limit is burst-based, per-issue, or quota-based. The IETF draft for rate limit headers defines structured fields such as RateLimit with parameters r for remaining quota and t for the effective window in seconds.

These headers are not guarantees. They reflect the server's view at the moment the response was generated. A positive remaining value can still lead to a 429 if another client consumes the last token before your next request arrives. Always treat the values as advisory and combine them with your own pacing logic.

  • Retry-After: preferred delay in seconds for both 429 and some 503 responses
  • X-RateLimit-Reset: ISO 8601 timestamp when the current window ends
  • RateLimit-Reason: scope identifier such as jira-burst-based or jira-quota-tenant-based
  • RateLimit and RateLimit-Policy: structured fields from the IETF draft
Core rule Treat every response as carrying current limit information. When a 429 arrives, read RateLimit-Reason or Retry-After first, then pause only the limited scope instead of halting the entire client.

Responding to a 429 without stalling the whole client

A 429 response blocks only the scope named in RateLimit-Reason. When the reason is jira-burst-based, slow requests to that single endpoint and method. When the reason is jira-quota-tenant-based, pause all requests to that tenant until the Retry-After period passes. Other endpoints and other tenants remain available.

Record the block at the scope level rather than in each thread. Multiple concurrent requests often receive identical 429 responses at the same moment. A shared block prevents every thread from starting its own independent backoff and waking together to hit the limit again.

  • Retry only requests that are safe to repeat (GET, PUT, DELETE are usually safe)
  • Never retry a POST that creates a resource unless you can detect duplicates
  • Cap total wait time and retry count so a long quota window does not hang the caller

Pacing requests and capping concurrency

The most frequent cause of 429 responses is sending too many requests at once. Promise.all on hundreds of keys or launching dozens of workers quickly exhausts burst capacity even when the steady-state rate is respected. Limit in-flight requests to a small number, typically five to ten, across the entire application rather than per thread or process.

Design around the steady-state rate instead of the burst buffer. The burst allowance absorbs occasional spikes, but relying on it for normal operation produces repeated throttling. Spread traffic over time and reduce pressure on any single endpoint and method combination.

  • Apply the same concurrency cap to the whole app, not per worker
  • Pace requests to the documented steady-state rate for each endpoint
  • Use token-bucket logic locally to smooth bursts before they reach the server

Adding jitter and respecting scope-specific delays

When Retry-After is present, wait at least that many seconds. If the header is missing, fall back to X-RateLimit-Reset or a short exponential backoff with jitter. Jitter prevents multiple clients that were limited together from retrying in lockstep and recreating the problem.

For burst limits the Retry-After value is often one second. Treat that as the minimum and apply exponential growth on subsequent 429 responses for the same scope. Reduce the request rate that triggered the limit rather than simply waiting and repeating the same pattern.

  • Add a small random delay to every backoff calculation
  • Back off only the limited scope identified by RateLimit-Reason
  • Return the response to the caller instead of retrying when the required wait exceeds your configured maximum

Putting the pieces together in client code

A well-behaved client combines three behaviors: it paces requests to the steady-state rate, caps concurrency across the whole application, and reacts to 429 responses by reading the reason header and waiting only for the affected scope. The same client continues sending requests to other endpoints and other tenants while one scope is blocked.

Test the logic with synthetic 429 responses and varying Retry-After values. Verify that a limit on one endpoint does not stall unrelated work and that the client eventually succeeds once capacity is restored. These checks catch the common failure modes before they appear in production.
