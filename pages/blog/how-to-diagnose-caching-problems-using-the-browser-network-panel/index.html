How to Diagnose Caching Problems Using the Browser Network Panel

Web pages often load old CSS, scripts, or images even after you edit the files on the server. The browser Network panel reveals whether a resource came from memory cache, disk cache, or a fresh download. By reading the Status, Size, and Timing columns you can tell whether a stale copy is blocking your changes and what steps will force an update without guessing.

Open the panel and reload with cache disabled

Open DevTools with Control+Shift+I or Command+Option+I. Switch to the Network tab. Check the Disable cache box so every reload bypasses the browser cache. This setting only applies while DevTools stays open.

Click the reload button or press Control+Shift+R. The Requests table now lists every resource the page actually fetched from the network. Compare this list with a normal reload later to see which items were previously served from cache.

The disable cache option provides a baseline view of network activity without any stored copies interfering. After running a test with the box checked, uncheck it and perform a standard reload to observe differences in which resources load from local storage instead of the server. This comparison helps isolate whether a particular file is the source of outdated content on the page.

  • Disable cache works only while DevTools is open.
  • A normal reload may still use validators such as If-Modified-Since.
  • Hard reload (Control+Shift+R) forces a new download in most cases.
Quick check Look for (from memory cache) or (from disk cache) in the Size column. These entries usually show status 200 even though no network request occurred.

Read status codes and size labels for cache behavior

A 200 status with a small transferred size usually means a fresh response. A 304 status means the server told the browser the cached copy is still valid. In the Size column you may also see the literal text (from memory cache) or (from disk cache). These indicate the browser never contacted the server at all.

Hover over the status code to see any extra messages such as (blocked:origin) or CORS errors. These appear when a cached cross-origin resource fails validation even though the file itself is present locally.

Status and size details together give a clear picture of reuse versus fresh retrieval. When a resource shows a 200 code paired with a large transferred byte count, it confirms the browser pulled new data over the network. In contrast, entries labeled from memory or disk cache with minimal or zero transferred size confirm no server contact happened, allowing quick identification of items that may need manual clearing if updates are not appearing.

  • 304 means the cached copy was reused after a quick check.
  • (from memory cache) is the fastest and most common for same-origin scripts.
  • A 200 with large transferred bytes shows the resource was downloaded again.

Inspect timing to find stalled or queued cache checks

Select any request and open the Timing tab. Queueing time appears when the browser waits for an available connection or checks the disk cache. Stalled time can also include service worker preparation before the request proceeds.

Long Waiting (TTFB) values on a 304 response show the server took time to validate the cache. Content Download time stays near zero for cached items because the browser reads from local storage instead of the network.

Breaking down the timing phases reveals hidden delays even when a resource ultimately comes from cache. Queueing often captures the moment spent looking up disk entries, while extended Waiting phases on validation responses point to server-side checks that still occur. Reviewing these breakdowns across multiple requests helps determine whether cache lookups themselves are contributing to slow page loads or if other phases require attention.

  • Queueing often includes disk cache lookup time.
  • ServiceWorker Preparation appears only when a service worker is active.
  • Hover the Waterfall column for a quick visual of each phase.

Handle failed or blocked resources that appear cached

A red row with status (failed) or (blocked:devtools) means the resource never loaded. Even if the file exists in cache, a new policy or certificate error can prevent reuse. Check the Headers tab for the exact blocking reason.

Use the Search tab (Control+F) to scan all headers and responses for Cache-Control or Expires values. This quickly shows whether a resource was intentionally cached for a long period.

When a request fails despite prior caching, examining header details pinpoints the exact cause such as policy changes or validation blocks. Searching across all recorded entries for cache-related headers surfaces long-lived directives that may explain why updates remain hidden. Clearing site data through the Application panel offers one route to reset such entries when repeated reloads do not resolve the issue.

  • Right-click a failed request and choose Block request URL to test page behavior without it.
  • Clear site data from the Application panel when cache entries refuse to update.
  • Service workers can serve their own cached responses; check the Application panel for those entries.

Compare Chrome and Firefox cache indicators

Chrome shows explicit cache labels in the Size column and a separate Cache tab for 304 responses. Firefox displays similar information in the Cache tab of the request details and lists Last fetched and Expires dates. Both browsers let you right-click a request to copy the URL or open it in a new tab for verification.

Firefox also records the number of times a resource was fetched in the current session. Use this count to spot resources that reload repeatedly instead of staying cached.

Each browser surfaces cache details in slightly different locations, yet both provide enough information to confirm reuse or fresh fetches. Chrome surfaces labels directly in the main table while Firefox separates device and size data in its dedicated tab. Cross-checking the same request in both tools confirms consistent behavior and helps decide whether a hard reload or full site data clear will address the observed problem.

  • Chrome Timing tab includes Proxy negotiation and ServiceWorker Preparation phases.
  • Firefox Cache tab shows Device (disk or memory) and Data size separately.
  • Both panels update live while you interact with the page.
